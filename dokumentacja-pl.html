PZT Rankingi

Offline aplikacja na Androida z rankingami Polskiego Związku Tenisowego (PZT) — dokumentacja techniczna.

Opis

PZT Rankingi to w pełni offline'owa aplikacja na Androida, która odzwierciedla i udostępnia dane rankingowe publikowane przez Polski Związek Tenisowy (portal.pzt.pl) — rankingi zawodników w kategoriach wiekowych, historię meczów, porównania head-to-head, kalendarz turniejów oraz drabinki. Aplikacja powstała na potrzeby akademii tenisowej (Akademia Tenisowa Zabrze), żeby trenerzy i zawodnicy mieli szybki dostęp do danych rankingowych bez konieczności stałego połączenia z internetem czy serwera w chmurze.

Brak serwera w chmurze Każde pobranie danych i cały stan aplikacji żyje wyłącznie na telefonie. Aplikacja nie komunikuje się z żadnym własnym serwerem — jedynym zewnętrznym punktem kontaktu jest publiczna strona PZT.

Architektura

Aplikacja to React SPA opakowane w Capacitor. Warstwa interfejsu powstała pierwotnie pod backend w Pythonie (FastAPI); zamiast przepisywać cały interfejs od nowa, logikę backendu przeniesiono do JavaScriptu działającego na telefonie i podpięto przez nakładkę na fetch() — dzięki temu te same wywołania fetch(`${API_BASE}/players/...`), które interfejs zawsze wykonywał, są dziś przechwytywane lokalnie zamiast trafiać do sieci.

Interfejs React (App.jsx) │ fetch(`${API_BASE}/...`) ▼ fetchShim.js — podmienia globalny fetch() │ ▼ localApi.js — router ścieżek (dispatch), odwzorowuje dawne REST API │ ├──▶ storage.js — odczyt/zapis lokalnych plików JSON │ z rankingami (Capacitor Filesystem) │ └──▶ src/native/pzt/* — scrapery uruchamiane na żądanie, jeden │ moduł na typ danych (profil zawodnika, │ mecze, H2H, drabinki/plan gier/selekcja │ turnieju, ...) ▼ CapacitorHttp — natywne zapytanie HTTP, omija ograniczenia CORS narzucane przez WebView │ ▼ portal.pzt.pl — odpowiedzi HTML, parsowane po stronie aplikacji przez DOMParser

Dlaczego nakładka na fetch(), a nie przepisanie interfejsu?

Ekran React (App.jsx, ok. 30 miejsc wywołań) mówił już czystym, REST-owym kontraktem do backendu FastAPI. Przeniesienie logiki backendu do JavaScriptu i odpowiadanie na ten sam kontrakt lokalnie oznaczało, że interfejs nie wymagał żadnych zmian — nowe są wyłącznie fetchShim.js i localApi.js. Dzięki temu migracja do w pełni offline'owej aplikacji była niskiego ryzyka i przyrostowa: kolejne moduły przenoszono i weryfikowano jeden po drugim, porównując wynik z oryginalną implementacją w Pythonie jako punktem odniesienia.

Model danych i scrapingu

Wszystkie dane rankingowe są pobierane bezpośrednio z publicznych stron PZT — nie ma tu żadnego kontraktu API ze strony PZT, więc parsowanie podąża za aktualną strukturą HTML strony i jest utrzymywane wraz z jej zmianami.

Rankingi — cache'owane, odświeżane co miesiąc

Miesięczne migawki rankingów per kategoria/płeć (U12 / U14 / U16 / U18 / SENIOR × K/M) są zapisywane jako osobne pliki JSON ({KATEGORIA}_{PŁEĆ}_{ROK}_{MIESIĄC}.json) i indeksowane na żądanie. Aplikacja automatycznie sprawdza dostępność nowych miesięcznych rankingów, a dodatkowo pozwala na import danych archiwalnych na żądanie.

Dane zawodników i turniejów — pobierane na żądanie, bez masowego pobierania

Historia meczów, statystyki head-to-head, kalendarz turniejów, drabinki/plany gier/listy selekcji nigdy nie są pobierane masowo z góry. Każdy z tych zasobów jest pobierany dopiero, gdy konkretny ekran go potrzebuje (np. otwarcie profilu zawodnika albo drabinki turnieju), z lekkim lokalnym cache'owaniem, żeby unikać zbędnych powtórnych zapytań. Dzięki temu obciążenie serwerów PZT ze strony aplikacji jest proporcjonalne do rzeczywistego użycia.

Eksport i import

Użytkownik może wyeksportować pełne archiwum rankingów do jednego pliku JSON przez systemowe menu „Udostępnij” (na Dysk, e-mailem, na kartę SD, na inny telefon…) i zaimportować je z powrotem tą samą drogą — przydatne do kopii zapasowych i przenoszenia danych na nowy telefon. Obejmuje to wyłącznie archiwum rankingów — ustawienia per urządzenie (ulubieni, motyw) żyją w lokalnym magazynie przeglądarki i nie są częścią eksportu.

Budowanie i wydawanie

Cały proces wydawania działa w GitHub Actions — nie jest potrzebny lokalny Android Studio:

  1. npm ci — instalacja zależności JS
  2. npm run build — produkcyjny build Vite (VITE_APP_VERSION ustawiane na numer przebiegu workflow)
  3. npx cap sync android — synchronizacja builda webowego z projektem Android w Capacitorze
  4. Odtworzenie klucza podpisującego z zaszyfrowanych sekretów GitHub
  5. ./gradlew assembleRelease — budowa podpisanego APK produkcyjnego, z versionCode/versionName powiązanym z numerem przebiegu workflow
  6. Dołączenie APK do prywatnego GitHub Release (pełna historia buildów, przechowywana bezterminowo) i publikacja najnowszego builda na tej stronie

Wersjonowanie

versionCode (liczba, którą Android wykorzystuje, żeby zdecydować czy dany build jest aktualizacją) jest równy numerowi przebiegu workflow budującego w GitHub Actions — czyli rosnącej liczbie całkowitej, inkrementowanej przy każdym uruchomieniu. To gwarantuje, że każde wydanie ma ściśle wyższy numer wersji, więc instalacja nowego APK zawsze aktualizuje poprzednią wersję w miejscu.

Środowisko developerskie lokalnie

npm install
npm run dev       # serwer developerski Vite, magazyn danych tylko w przeglądarce
npm run build     # build produkcyjny → dist/
npx cap sync android   # synchronizacja z natywnym projektem Android

Uwaga: poza natywną powłoką Android aplikacja korzysta z zapasowego magazynu w pamięci przeglądarki, a zapytania sieciowe do portal.pzt.pl podlegają standardowym ograniczeniom CORS przeglądarki — niektóre ścieżki scrapingu działają w pełni tylko na prawdziwym urządzeniu lub emulatorze, gdzie CapacitorHttp omija to ograniczenie.
