Overview

PZT Rankingi is a fully offline Android application that mirrors and browses ranking data published by the Polish Tennis Association (portal.pzt.pl) — player rankings by age category, match history, head-to-head comparisons, tournament calendars and draws. It was built for a tennis academy (Akademia Tenisowa Zabrze) to give coaches and players quick access to ranking data without needing a live connection or a backend server.

No cloud backend Every data fetch and every piece of app state lives entirely on the phone. There is no server this app talks to other than PZT's own public website.

Architecture

The app is a Capacitor-wrapped React single-page application. The UI layer was originally built against a Python/FastAPI backend; rather than rewrite the UI, the backend was ported to on-device JavaScript and wired in through a fetch() shim — so the same fetch(`${API_BASE}/players/...`) calls the UI always made now get intercepted locally instead of going over the network.

React UI (App.jsx) │ fetch(`${API_BASE}/...`) ▼ fetchShim.js — installs a global fetch() override │ ▼ localApi.js — path router (dispatch), mirrors the old REST API shape │ ├──▶ storage.js — reads/writes cached ranking JSON files │ (Capacitor Filesystem on device) │ └──▶ src/native/pzt/* — on-demand scrapers, one module per data type │ (player profile, matches, H2H, tournament │ draws/schedule/acceptance lists, ...) ▼ CapacitorHttp — native HTTP request, bypasses WebView CORS │ ▼ portal.pzt.pl — HTML responses, parsed client-side with DOMParser

Why a fetch() shim instead of rewriting the UI?

The React screen (App.jsx, ~30 call sites) already spoke a clean REST-shaped contract to a FastAPI backend. Porting the backend logic to JavaScript and answering that same contract locally meant the UI needed zero changes — only fetchShim.js and localApi.js are new. This kept the migration to a fully offline app low-risk and incremental: modules were ported and verified one endpoint at a time against the original Python implementation as a reference.

Data & scraping model

All ranking data is scraped directly from PZT's public pages — there is no API contract with PZT, so parsing follows the site's current HTML structure and is maintained accordingly if that structure changes.

Rankings — cached, refreshed monthly

Monthly ranking snapshots per category/gender (U12 / U14 / U16 / U18 / SENIOR × K/M) are stored as individual JSON files ({CATEGORY}_{GENDER}_{YEAR}_{MONTH}.json) and indexed on demand. The app checks for new monthly rankings automatically and also supports on-demand import of archival data.

Player & tournament data — fetched on demand, no bulk crawling

Match history, head-to-head records, tournament calendars, draws/brackets, schedules and acceptance lists are never pre-fetched in bulk. Each is scraped only when a specific screen requests it (e.g. opening a player's profile, or a tournament's draw), with lightweight local caching to avoid redundant requests. This keeps the app's footprint on PZT's servers proportional to actual usage.

Export & import

Users can export the full ranking archive as a single JSON file via the native share sheet (to Drive, email, SD card, another device, …) and re-import it the same way — useful for backups and moving data to a new phone. This only covers ranking archive files; per-device preferences (favorites, theme) live in local storage and are not included.

Building & releasing

The release pipeline runs entirely in GitHub Actions — no local Android Studio setup is required:

  1. npm ci — install JS dependencies
  2. npm run build — Vite production build (VITE_APP_VERSION set to the workflow run number)
  3. npx cap sync android — sync the web build into the Capacitor Android project
  4. Restore the release keystore from encrypted GitHub secrets
  5. ./gradlew assembleRelease — build a signed release APK, with versionCode/versionName tied to the workflow run number
  6. Attach the APK to a private GitHub Release (full build history, kept indefinitely) and publish the latest build to this page

Versioning

versionCode (the number Android uses to decide whether a build is an upgrade) equals GitHub's workflow run number for the build workflow — a monotonically increasing integer, one per triggered run. This guarantees every release strictly increases the version, so installing a new APK always upgrades in place.

Local development

npm install
npm run dev       # Vite dev server, browser-only storage backend
npm run build     # production build → dist/
npx cap sync android   # sync into the native Android project

Note: outside the native Android shell, the app falls back to an in-memory/browser storage backend and network requests to portal.pzt.pl are subject to normal browser CORS — some scraping flows only work end-to-end on a real device or emulator, where CapacitorHttp bypasses that restriction.
